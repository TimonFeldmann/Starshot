# AGENTS.md

## Layout

- Git repo root is this workspace folder itself (the old `Starshot/` subfolder nesting
  was flattened on 2026-10-30). Run all git/build commands from here.
- `src/Starshot` — WinUI 3 / WinAppSDK app (C#, `net10.0-windows10.0.26100.0`, platforms x64/arm64, RID win-x64 default)
- `src/Starshot.Language` — resx resources + checked-in `Lang.Designer.cs`
- `src/Starshot.Launcher` — C++ launcher (vcxproj; needs VS MSBuild, CI builds it; portable-line only, not part of the installer)
- `src/Starshot.Tests` — xunit.v3 HDR integration suite. No ProjectReference to the app: the tests drive the built `build\app\Starshot.exe`, the C++ signal host, and ffmpeg as child processes. Plain `dotnet test` is always safe — tests self-skip when a prerequisite is missing
- `tools/` — test infra + throwaway probes: `HdrSignalHost` (C++ HDR stimulus host; `build.ps1`, needs MSVC), `ffmpeg/` (gitignored; `tools/fetch-ffmpeg.ps1` downloads a pinned build into `tools\ffmpeg\bin`, then no env var is ever needed), `codecs/build-codecs.ps1` (copies the pre-built encoder DLLs from `tools\codecs\dlls` into `build\codecs` and compiles the C shim), probes `WinmdDump` / `ApiDump` / `CodecProbe` / `IconProbe` / `Win2dProbe` / `CodecsSmoke`. `WinmdDump`: `dotnet run --project tools/WinmdDump <winmd-path> [filter]` dumps a projection's API surface
- `scripts/run-hdr-test.ps1` — interactive driver for the HDR suite (mode + phase length)
- `deploy-release.ps1` — kachina installer build + optional launch (local mirror of the CI installer line; installs to `C:\Program Files\Starshot`)
- `build/` is gitignored, flat layout: `build\app` (Debug), `build\release\app` (Release publish), `build\codecs` (encoder DLLs)
- `README.md` — authoritative docs (shortcuts, build steps, the "Integration tests" section, i18n, contributor rules); `docs/` holds the localized READMEs

## Build / run loop (Debug)

1. `Stop-Process -Name Starshot -Force` first — a running instance locks `build\app\Starshot.exe` (MSB3027/MSB3021 copy failure)
2. `dotnet build src/Starshot/Starshot.csproj -c Debug -p:Platform=x64` (`-p:Platform` is required; the csproj only defines x64/arm64)
3. `Start-Process .\build\app\Starshot.exe`

- Debug builds are intentionally self-contained (csproj comment: dev machine runtime broken) → slow; not a bug
- Release: `dotnet publish src/Starshot/Starshot.csproj -c Release -p:Platform=x64` (trimmed + R2R; `CopyLauncher` target copies the C++ launcher into `build\release\`)
- csproj `CETCompat=false` is intentional (inherited from the Starward lineage, unverified but working — the comment says leave it) — don't remove
- Global hotkeys: Alt+W full-screen capture, Alt+Q region (save + clipboard), Alt+A region (clipboard only), Alt+O OCR → clipboard. A capture opens the Screenshot Editor (Settings toggles)

## HDR integration test suite (`src/Starshot.Tests`)

- Run: `pwsh scripts\run-hdr-test.ps1` (asks: with/without recording, phase length) or `dotnet test src/Starshot.Tests` (self-skips without prerequisites)
- Prerequisites: a display in HDR mode at the row's resolution; encoder DLLs in `build\codecs` (auto-runs `tools\codecs\build-codecs.ps1`, which needs the VS C++ workload + local encoder sources); ffmpeg/ffprobe (resolution order: `STARSHOT_TEST_FFMPEG_DIR` → gitignored `tools\ffmpeg\bin` → PATH)
- Recording rows: (3840×2160, 10000) / (2560×1440, 10000) / (3840×2160, 5000) / (3840×2160, 240) nits. Each row paints four color phases (GREEN/RED/BLUE/YELLOW, `STARSHOT_HDR_PHASE_SECONDS` each, default 5 s, clamped 2..300) via the C++ signal host and takes ONE automated `--record-test` window capture (4 × phase), checked against the analytic ST 2084 + BT.2020 ground truth (±6 codes). A row that fails with all-neutral frames (e.g. 4232-nit frames on the 5000-n row) is a WGC session-init transient — just re-run the row
- Play-only variant `HdrFlatFieldPlay` (`STARSHOT_HDR_PLAY_SECONDS`, default 120 s, clamped 15 s..1 h): paints the fields for your own manual recording, no automated capture
- The suite **never kills the user's Starshot instance** (the record-test child is headless and coexists). While the app is running the suite reuses the existing `build\app` (a running exe locks its build output) — close the app to test freshly changed source. Keep the Starshot window unfocused during a row: the capture follows the foreground window
- Global keys (no console focus needed): ESC ends the suite, Space freezes the active row in place (resumes from exactly where it stopped). `run-hdr-test.ps1` prints each pause/resume/stop so a paused suite is distinguishable from a hung one
- This machine's WGC capture path carries deterministic color deviations (out-of-gamut YELLOW shift at 5000/10000 nits; a mid-band bulge on 5000-nit GREEN). Those fields assert against the measured machine codes (`MachineExpectation` in `HdrRecordingTests.cs`), not the standard — do not "fix" them back. Full history: `hdr-dim-troubleshooting.md`
- Hidden CLI flags (DEBUG builds, see `Program.cs`): `Starshot.exe --record-test [fullscreen|window] ...` (headless record-test host) and `--hdr-probe` (per-display HDR-state probe)

## WinAppSDK projection quirks

This WinAppSDK 1.8 projection's API surface is a **subset** of standard WinUI. Verify any API against the projection winmd before assuming it exists: `%USERPROFILE%\.nuget\packages\microsoft.windowsappsdk.winui\<ver>\metadata\Microsoft.UI.Xaml.winmd` (the WinUI subpackage version can differ from the metapackage in csproj). All below were hit in practice:

- `ToolTip`/`ToolTipService` exist under UWP-style names in `Microsoft.UI.Xaml.Controls`; explicitly showing a standalone `ToolTip` (`IsOpen=true`) crashes natively (0xc000027b in Microsoft.UI.Xaml.dll). Codebase pattern instead: themed Canvas+Border hover hint (see `ScreenshotEditWindow` `Canvas_ToolTips`)
- No `ItemsControl.ItemSpacing` (XAML compiler WMC0011)
- No `Microsoft.UI.Dispatching.DispatcherTimer` — use `DispatcherQueue.CreateTimer()` (unqualified; the fully-qualified form fails CS0120); `DispatcherQueueTimer` has `.Interval`/`.Tick` (see `InAppToast.cs`)
- `Border` has no `Foreground` (put it on the inner TextBlock)
- Children of a 0×0 `Grid` don't render → use a `Canvas` for overlay cursors (see `Canvas_BrushPreview`)
- `Image`'s coordinate origin is the letterboxed rendered content, not the control bounds → convert pointer positions with `TransformToVisual`
- Win2D (`Microsoft.Graphics.Canvas`) collides with XAML `Canvas` — fully qualify `Microsoft.UI.Xaml.Controls.Canvas` when both are imported. Win2D ships via `Starward.Win2D` (`Microsoft.Graphics.Win2D` is `ExcludeAssets="all"`)
- `ObservableObject` comes from `CommunityToolkit.Mvvm.ComponentModel`
- `Panel.Children.Insert` needs a UIElement cast

Package pins: `CommunityToolkit.WinUI.Controls.Segmented` must not be updated (csproj comment: upstream PR pending); WinAppSDK metapackage is 1.8.260529003.

## Diagnostics

- Serilog logs: `%LOCALAPPDATA%\Starshot\log\Starshot_Debug_YYMMDD.log`; config: `%LOCALAPPDATA%\Starshot\config.sjson`
- Native XAML crashes never reach Serilog — check the Windows Application event log (Event 1000, faulting module)
- This dev box is dual-display: synthetic `mouse_event` ABSOLUTE coords map onto the whole virtual screen and are unreliable. Verify UI behavior with the user's real mouse, using temporary `_logger.LogDebug("[DBG] ...")` lines read from the Serilog log — remove them before committing
